# Conversational planning and scheduled notifications

The conversational agent reads Calendar events, finds real openings, retrieves learned outcome estimates, and inspects confirmed session notes. Each turn permits at most four model decisions and a 90-second overall budget, with 30 seconds per model call. The Grok 4.7 planner uses low reasoning effort to reduce latency; the model itself is unchanged. Recent conversation, displayed proposals, replay results, and tool receipts persist privately in `data/agent-turns/`.

A study booking requires a follow-up confirmation of the exact displayed offer. Offers expire after ten minutes. Booking rechecks availability and uses a deterministic Calendar event ID to recover uncertain responses. It reserves time; it does not automatically start tracking a session. Conflict reviews keep their existing eligible-event rules, private approval links, event-version checks, and explicit approval requirement. General user requests cannot grant additional tools or bypass these checks.

The background scheduler sends a morning brief at **8:30 a.m. America/Los_Angeles** and an event check-in **10 minutes before timed events**. It uses the single chat already connected through study reminders, respects quiet hours and snoozes, and pauses when reminders are disabled. Check-ins wait during pending ratings or agent confirmations. The bot must remain running and connected; Vercel does not run this scheduler. A restart before 10 a.m. can catch up a missed brief. There is no overnight catch-up. All-day, cancelled, declined and transparent events do not trigger pre-event messages. Simultaneous events are grouped.

Notification attempts are persisted before sending, preventing duplicate messages after an uncertain delivery response. This favors avoiding repeat messages over guaranteed delivery. State is private and stored in `data/daily-brief/`. Text `morning brief` for an on-demand brief, `morning brief off` / `on` / `status`, or `event checkins off` / `on` / `status`. `reminders off` pauses both features. These commands are a fallback; ordinary planning requests can be phrased naturally.

Try “Find me 30 minutes tomorrow afternoon to study,” “What have my study ratings been telling you?” or “Can you check my schedule for conflicts?” After a displayed study offer, “book it” confirms that offer. The agent cannot independently move meetings or arbitrary events. Existing location and calendar proactivity policies are still separate from conversational planning. The optional notes inform LLM reasoning, not the LinUCB feature vector. LinUCB continues to update from linked ratings; the foundation language model is not fine-tuned.

Applied review receipts upload immediately and retry from the protected review worker. The dashboard separates pending, approved/applied and closed reviews. Its private code must belong to the same chat as the review. Restart the review worker from the bot project directory so it loads the existing backend configuration; do not copy backend secrets into the website.

Optional cloud planning activity requires `supabase/015_agent_runs.sql` and deployment of `supabase/functions/model-dashboard`. The audit outbox sends only tool names, success flags, outcome and timestamps; no chat text, tool payloads, precise locations or private links. Missing migration leaves receipts queued locally and does not stop planning. Existing session/rating sync is unchanged. The CLI needs a Supabase management login to deploy the function; a project database secret is not a management access token.

The architecture follows a bounded observe–decide–validate–execute–verify pattern, also used by [Burrow](https://github.com/jerryjlwang/Burrow). No Burrow source code was copied. It remains a contextual-bandit reward model plus a tool-using LLM, rather than an end-to-end reinforcement-learning policy.

## Place recommendations

The learning tool now exposes ranked, recorded place/setup profiles, including partially known profiles, with estimated productivity and mood, matching personal-session counts, uncertainty and profile age. Rankings use a common 45-minute duration. Current location is read through the same freshness checks and UW building matcher as the explicit location command. Only the estimated building/category and capture time reach the planner; precise coordinates and sender identifiers stay out of its tool receipt. The lookup does not save a place or start tracking a session. The sender is resolved from the current inbound message, with the existing per-chat address as a fallback.

Natural place questions now reach this tool-using conversational path instead of the older isolated recommendation reply. Location failure remains independent of history availability, so missing GPS cannot erase learned place evidence. Historical category scores are not scores for named buildings, proof of current conditions, opening hours or travel-time estimates. Personal history is kept separate from starter-profile evidence in the tool receipt.

## Local text-provider selection

An optional, untracked `data/runtime/text-provider.json` containing `{"provider":"gemini"}` or `{"provider":"xai"}` overrides the existing AI_PROVIDER value for local bot runs. It contains no API key. When absent, AI_PROVIDER and the existing xAI default retain their previous behavior. The selected provider still uses its existing environment credential and model setting. This supports switching away from a provider billing outage without reading or rewriting .env. The active installation was tested with Gemini 3.5 Flash; user-specific provider choices are not committed.
